1. Architecture Overview

This pipeline ingests real-time bus and tube arrival predictions from the Transport for London (TFL) API, streams them through Kafka, and loads them into both HBase (for low-latency lookups) and HDFS Parquet (for analytics via Hive).

Pipeline Flow

TFL Arrivals API (REST)  →  send_data_to_kafka.py (Producer)  →  Kafka Topic: tfl_arrivals

                                                                 ↙                         ↘
write_kafka_to_hbase.py               spark_streaming_tfl.py
(HBase Consumer)                        (Spark Structured Streaming)
        ↓                                                 ↓
HBase Table: tfl_arrivals               HDFS Parquet
(row key: station_vehicle_ts)                        ↓
                                          Hive External Table
                                          yamini_tfl_proj.tfl_spark_arrivals

Component Roles

ComponentRoleTechnology
TFL APISource of real-time bus/tube arrival predictionsREST API (JSON)
KafkaMessage broker — decouples producer from consumersApache Kafka (CDH)
ProducerPolls TFL API every 30s, publishes JSON to KafkaPython + kafka-python
HBase ConsumerReads from Kafka, writes records to HBase in batches of 20Python + kafka-python + HBase Shell
Spark StreamingReads Kafka micro-batches every 60s, writes Parquet to HDFSPySpark Structured Streaming
HiveSQL analytics layer on top of Parquet filesHive 3.1.3 / Beeline

Topic design: 4 partitions allow both consumers (HBase + Spark) to read in parallel. With replication-factor 1 this is a single-broker setup — use 3 for production.

How Kafka Works in This Pipeline

ConceptThis Pipeline
Topictfl_arrivals — one topic for all arrival data
Producersend_data_to_kafka.py — one producer, no consumer group

4. Step 2 – TFL API → Kafka Producer

The producer polls the TFL Arrivals API every 30 seconds and publishes each arrival prediction as a JSON message to the tfl_arrivals Kafka topic.

File: kafka/send_data_to_kafka.py

#!/usr/bin/env python3
import json, time, requests
from kafka import KafkaProducer

KAFKA_BROKER = 'ip-172-31-6-42.eu-west-2.compute.internal:9092'
TOPIC        = 'tfl_arrivals'
API_KEY      = 'YOUR_TFL_API_KEY'
RUN_SECS     = 3600   # run for 1 hour

# A sample of London bus/tube stop IDs
STOP_IDS = ['490003035W', '490000077A', '490000123E', '940GZZLUWSP']

producer = KafkaProducer(
    bootstrap_servers=KAFKA_BROKER,
    value_serializer=lambda v: json.dumps(v).encode('utf-8')
)

start = time.time()
while time.time() - start < RUN_SECS:
    for stop_id in STOP_IDS:
        url = f'https://api.tfl.gov.uk/StopPoint/{stop_id}/Arrivals?app_key={API_KEY}'
        resp = requests.get(url, timeout=10)
        if resp.status_code == 200:
            for arrival in resp.json():
                record = {
                    'id':              arrival.get('id'),
                    'vehicleId':       arrival.get('vehicleId'),
                    'stationName':     arrival.get('stationName'),
                    'lineName':        arrival.get('lineName'),
                    'platformName':    arrival.get('platformName'),
                    'expectedArrival': arrival.get('expectedArrival'),
                    'timeToStation':   arrival.get('timeToStation'),
                    'currentLocation': arrival.get('currentLocation'),
                    'direction':       arrival.get('direction'),
                    'destinationName': arrival.get('destinationName'),
                    'timestamp':       arrival.get('timestamp'),
                }
                producer.send(TOPIC, value=record)
    producer.flush()
    print(f"Batch sent. Sleeping 30s...")
    time.sleep(30)

producer.close()
print("Producer finished.")

Key Points

  • Each TFL arrival prediction has a unique id field — used later for deduplication
  • The producer runs for 3600 seconds (1 hour) then exits cleanly
  • producer.flush() ensures all messages are sent before sleeping
  • Messages are serialised as UTF-8 JSON strings

5. Step 3 – Kafka → HBase Consumer

The HBase consumer reads arrival messages from Kafka and writes them to HBase in batches of 20 records using the HBase shell.

First: Create the HBase Table

hbase shell
hbase(main):001:0> create 'tfl_arrivals', 'cf'
hbase(main):002:0> list
hbase(main):003:0> exit
Row key design: {stationName}_{vehicleId}_{timestamp} — this ensures each unique arrival event gets its own row and allows fast lookups by station + vehicle.

File: kafka/write_kafka_to_hbase.py

#!/usr/bin/env python3
import json, logging, subprocess
from kafka import KafkaConsumer

KAFKA_BROKER = 'ip-172-31-6-42.eu-west-2.compute.internal:9092'
TOPIC        = 'tfl_arrivals'
HBASE_TABLE  = 'tfl_arrivals'
GROUP_ID     = 'yamini_tfl_hbase_consumer'
BATCH_SIZE   = 20

logging.basicConfig(filename='/tmp/hbase_consumer.log', level=logging.INFO,
                    format='%(asctime)s %(levelname)s %(message)s')

def build_row_key(record):
    station   = record.get('stationName', '').replace(' ', '')
    vehicle   = record.get('vehicleId', '')
    timestamp = record.get('timestamp', '')
    return f"{station}_{vehicle}_{timestamp}"

def write_batch_to_hbase(records):
    commands = []
    for r in records:
        rk = build_row_key(r)
        commands.append(f"put '{HBASE_TABLE}', '{rk}', 'cf:station', '{r.get('stationName','')}'")
        commands.append(f"put '{HBASE_TABLE}', '{rk}', 'cf:vehicle', '{r.get('vehicleId','')}'")
        commands.append(f"put '{HBASE_TABLE}', '{rk}', 'cf:line',    '{r.get('lineName','')}'")
        commands.append(f"put '{HBASE_TABLE}', '{rk}', 'cf:arrival', '{r.get('expectedArrival','')}'")
    hbase_input = '\n'.join(commands) + '\nexit\n'
    subprocess.run(['hbase', 'shell', '-n'], input=hbase_input.encode('utf-8'),
                   stdout=subprocess.PIPE, stderr=subprocess.PIPE, timeout=60)
    logging.info("Wrote %d records to HBase", len(records))

consumer = KafkaConsumer(
    TOPIC,
    bootstrap_servers=KAFKA_BROKER,
    auto_offset_reset='latest',
    group_id=GROUP_ID,
    value_deserializer=lambda x: json.loads(x.decode('utf-8')),
    enable_auto_commit=True
)

batch, total = [], 0
for message in consumer:
    batch.append(message.value)
    if len(batch) >= BATCH_SIZE:
        write_batch_to_hbase(batch)
        total += len(batch)
        print(f"Written {total} records to HBase")
        batch = []

Run the consumer (background)

nohup python3 /home/consultant/yamini/tfl_Project1/kafka/write_kafka_to_hbase.py \
  > /tmp/hbase_consumer.log 2>&1 &

Verify HBase records

echo "count 'tfl_arrivals'" | hbase shell -n 2>/dev/null | grep -E "^[0-9]|row"
echo "scan 'tfl_arrivals', {LIMIT => 3}" | hbase shell -n 2>/dev/null

6. Step 4 – Spark Structured Streaming Job

The Spark job reads messages from Kafka as micro-batches every 60 seconds, parses the JSON, adds an ingestion timestamp, and writes Parquet files to HDFS.

File: spark/spark_streaming_tfl.py

#!/usr/bin/env python3
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, from_json, current_timestamp
from pyspark.sql.types import StructType, StructField, StringType, IntegerType

KAFKA_BROKER = 'ip-172-31-6-42.eu-west-2.compute.internal:9092'
KAFKA_TOPIC  = 'tfl_arrivals'
HDFS_OUTPUT  = '/tmp/yamini/tfl_spark_streaming/output'
CHECKPOINT   = '/tmp/yamini/tfl_spark_streaming/checkpoint'
RUN_SECS     = 3600

SCHEMA = StructType([
    StructField("id",              StringType(),  True),
    StructField("vehicleId",       StringType(),  True),
    StructField("stationName",     StringType(),  True),
    StructField("lineName",        StringType(),  True),
    StructField("platformName",    StringType(),  True),
    StructField("expectedArrival", StringType(),  True),
    StructField("timeToStation",   IntegerType(), True),
    StructField("currentLocation", StringType(),  True),
    StructField("direction",       StringType(),  True),
    StructField("destinationName", StringType(),  True),
    StructField("timestamp",       StringType(),  True),
])

def main():
    spark = SparkSession.builder \
        .appName("TFL_Spark_Streaming") \
        .config("spark.sql.parquet.writeLegacyFormat", "true") \
        .getOrCreate()
    spark.sparkContext.setLogLevel("WARN")

    raw = spark.readStream \
        .format("kafka") \
        .option("kafka.bootstrap.servers", KAFKA_BROKER) \
        .option("subscribe", KAFKA_TOPIC) \
        .option("startingOffsets", "latest") \
        .option("failOnDataLoss", "false") \
        .load()

    parsed = raw.select(
        from_json(col("value").cast("string"), SCHEMA).alias("d")
    ).select("d.*").withColumn("ingested_at", current_timestamp())

    query = parsed.writeStream \
        .format("parquet") \
        .option("path", HDFS_OUTPUT) \
        .option("checkpointLocation", CHECKPOINT) \
        .trigger(processingTime="60 seconds") \
        .start()

    print(f"Streaming started → topic: {KAFKA_TOPIC}  output: {HDFS_OUTPUT}")
    query.awaitTermination(RUN_SECS)
    query.stop()
    spark.stop()
    print("Spark Streaming completed successfully.")

if __name__ == '__main__':
    main()

Key Design Decisions

DecisionWhy
--master local[2]Avoids YARN orphan JVM issue. YARN mode: Python driver exits after 3600s but the JVM container stays alive, locking the checkpoint. Local mode couples the JVM to the Python process.
startingOffsets: latestOnly processes new messages — avoids reprocessing the full backlog on restart
trigger(processingTime="60 seconds")Writes one Parquet file per micro-batch per minute
checkpointLocationTracks which Kafka offsets have been processed — enables exactly-once semantics
failOnDataLoss=falsePrevents job failure if Kafka topic offsets are reset or messages expired
parquet.writeLegacyFormat=trueCompatibility with Hive 3.1.3 on CDH which uses older Parquet format

Submit the Spark job (background)

nohup spark-submit \
  --master local[2] \
  --name TFL_Spark_Streaming \
  --driver-memory 512m \
  --conf spark.sql.parquet.writeLegacyFormat=true \
  /home/consultant/yamini/tfl_Project1/spark/spark_streaming_tfl.py \
  > /tmp/spark_streaming.log 2>&1 &
echo "Spark PID: $!"

7. Step 5 – HDFS Directory Preparation

Before starting the Spark job, the HDFS output and checkpoint directories must be created and permissions set. This must be done on every fresh run to avoid checkpoint conflicts.

Clean and Recreate HDFS Directories

# Remove old output and checkpoint (clean slate for each run)
HADOOP_USER_NAME=hdfs hdfs dfs -rm -r -f -skipTrash /tmp/yamini/tfl_spark_streaming

# Recreate fresh directories
HADOOP_USER_NAME=hdfs hdfs dfs -mkdir -p /tmp/yamini/tfl_spark_streaming/output
HADOOP_USER_NAME=hdfs hdfs dfs -mkdir -p /tmp/yamini/tfl_spark_streaming/checkpoint

# Open permissions so consultant user can write
HADOOP_USER_NAME=hdfs hdfs dfs -chmod -R 777 /tmp/yamini/tfl_spark_streaming

echo "HDFS directories ready"

Check HDFS Output After Streaming Runs

# List Parquet files written
hdfs dfs -ls /tmp/yamini/tfl_spark_streaming/output

# Check total size
hdfs dfs -du -s -h /tmp/yamini/tfl_spark_streaming/output

# Count Parquet files
hdfs dfs -ls /tmp/yamini/tfl_spark_streaming/output | grep ".parquet" | wc -l
Checkpoint locking: If a previous Spark job crashed without releasing the checkpoint, a new job using the same checkpoint path may silently write 0 bytes. Always delete /tmp/yamini/tfl_spark_streaming before each fresh run with hdfs dfs -rm -r -f -skipTrash.

Expected HDFS Output

After the streaming job runs for a few minutes (at least 2 micro-batches), you should see:

Found 7 items
-rw-r--r-- 3 consultant ... /tmp/yamini/tfl_spark_streaming/output/part-00000-...parquet
-rw-r--r-- 3 consultant ... /tmp/yamini/tfl_spark_streaming/output/part-00001-...parquet
...
# Total: ~500 KB for 34,000 records
Success indicator: Each 60-second micro-batch produces one or more Parquet files. If you see files growing in HDFS, Spark is working correctly.

8. Step 6 – Hive External Table

Create a Hive external table pointing at the HDFS Parquet output. The table is "external" — Hive manages the metadata only; the data lives in HDFS and is written by Spark.

File: spark/hive_spark_table.sql

CREATE DATABASE IF NOT EXISTS yamini_tfl_proj;

DROP TABLE IF EXISTS yamini_tfl_proj.tfl_spark_arrivals;

CREATE EXTERNAL TABLE yamini_tfl_proj.tfl_spark_arrivals (
    id              STRING,
    vehicleId       STRING,
    stationName     STRING,
    lineName        STRING,
    platformName    STRING,
    expectedArrival STRING,
    timeToStation   INT,
    currentLocation STRING,
    direction       STRING,
    destinationName STRING,
    arr_timestamp   STRING,
    ingested_at     TIMESTAMP
)
STORED AS PARQUET
LOCATION '/tmp/yamini/tfl_spark_streaming/output';

SELECT COUNT(*) AS total_records FROM yamini_tfl_proj.tfl_spark_arrivals;

Run the SQL via Beeline

beeline -u 'jdbc:hive2://<HIVESERVER2_HOST>:10000/default' \
  -n consultant \
  -p 'your_password' \
  -f /home/consultant/yamini/tfl_Project1/spark/hive_spark_table.sql

Query the Table

# Total record count
SELECT COUNT(*) FROM yamini_tfl_proj.tfl_spark_arrivals;

# Records per tube line
SELECT lineName, COUNT(*) AS cnt
FROM yamini_tfl_proj.tfl_spark_arrivals
GROUP BY lineName
ORDER BY cnt DESC;

# Latest arrivals
SELECT stationName, lineName, expectedArrival, ingested_at
FROM yamini_tfl_proj.tfl_spark_arrivals
ORDER BY ingested_at DESC
LIMIT 20;
External vs Managed table: Because this is EXTERNAL, running DROP TABLE only removes the Hive metadata — the Parquet files in HDFS are not deleted. This is intentional: Spark owns the data, Hive just queries it.

SSH Authentication (sshpass)

The pipeline uses sshpass for password-based SSH — no key file required:

sshpass -p "your_password" ssh -o StrictHostKeyChecking=no \
  consultant@your-host "remote command here"
Common mistake: If you see Identity file not accessible: No such file or directory in the Jenkins logs, the pipeline is using SSH key auth (-i keyfile) but the key doesn't exist. Switch to sshpass password auth as shown above.

Why Scripts Are Downloaded via wget (not scp)

Jenkins runs on a different server. The Python scripts live in GitHub. Rather than copying from the Jenkins workspace (which requires network setup), the pipeline downloads the latest version directly from GitHub Raw URLs:

wget -q -O spark_streaming_tfl.py \
  https://raw.githubusercontent.com/YOUR_USER/TFL_Project/main/src/spark/spark_streaming_tfl.py

This means every build always uses the latest committed code.

12. Common Errors & Fixes

Error 1: kafka.group.id not supported

IllegalArgumentException: Kafka option 'group.id' is not supported as user-specified
consumer groups are not used to track offsets.
Cause: Spark 2.4's Kafka connector does not allow setting a consumer group ID.
Fix: Remove .option("kafka.group.id", ...) from your Spark code entirely. Spark manages offsets via the checkpoint directory.

Error 2: Spark writes 0 bytes to HDFS

hdfs dfs -du -s -h /tmp/yamini/tfl_spark_streaming/output
0  /tmp/yamini/tfl_spark_streaming/output
Cause: A previous Spark YARN job is still running as an orphan JVM. After its Python driver exited (after 3600s), the YARN container stays alive and reclaims the checkpoint directory on HDFS, silently blocking the new Spark job.
Fix: Use --master local[2] instead of YARN. In local mode, the JVM is tightly coupled to the Python process — when Python exits, the JVM exits. No orphan containers possible.

Error 3: No such file or directory for the Python script

python3: can't open file '/path/to/spark_full_load_tfl.py': [Errno 2] No such file or directory
Cause: You are SSH'd into the wrong machine. The script exists on the Cloudera edge node but you are on the Hadoop namenode (ec2-user@ip-172-31-3-85).
Fix: Either wget the script first, or SSH to the correct machine (consultant@your-cloudera-host) where Jenkins downloaded it.

Error 4: SSH Permission Denied in Jenkins

Warning: Identity file /var/lib/jenkins/.ssh/test_key.pem not accessible: No such file or directory.
ec2-user@host: Permission denied (publickey,...)
Cause: The Jenkinsfile uses ssh -i keyfile but the key file doesn't exist on the Jenkins server.
Fix: Replace ssh -i ${SSH_KEY} with sshpass -p "password" ssh in every stage of the Jenkinsfile.

Error 5: Hive returns 0 records

SELECT COUNT(*) FROM yamini_tfl_proj.tfl_spark_arrivals;
-- Result: 0
Cause: The Hive table was created before Spark wrote any Parquet files, OR the Spark job wrote 0 bytes (see Error 2).
Fix: Wait at least 5 minutes after starting Spark, verify Parquet files exist with hdfs dfs -ls, then re-run the Hive DDL.

13. Key Concepts Summary

ConceptExplanation
Spark Structured StreamingUses spark.readStream to continuously read Kafka. Each trigger interval produces one micro-batch.
Spark Batch (Full Load)Uses spark.read to read ALL Kafka messages at once from earliest to latest. One-shot job, not continuous.
Checkpoint DirectoryStores Kafka offsets and streaming state. Spark uses it to resume after failure and track exactly-once delivery.
startingOffsets: latestStreaming job only reads new messages from the moment it starts. Use earliest to read the entire backlog.
local[2] vs YARNlocal[2] — runs in the same JVM as the driver, 2 threads. YARN — submits to the cluster resource manager, can create orphan containers.
External Hive TableHive stores only metadata. The actual data files are in HDFS and managed by Spark. DROP TABLE removes metadata only.
HADOOP_USER_NAME=hdfsImpersonates the HDFS superuser for a single command. Needed when your Linux user doesn't have HDFS write permissions.
nohup + &nohup prevents the process from being killed when the SSH session ends. & runs it in the background so Jenkins can continue to the next stage.
failOnDataLoss=falsePrevents Spark job failure if Kafka topic offsets have been reset (e.g. topic deleted and recreated).
writeLegacyFormat=trueWrites Parquet in a format compatible with older Hive/CDH versions that don't support the newer INT96 timestamp encoding.
